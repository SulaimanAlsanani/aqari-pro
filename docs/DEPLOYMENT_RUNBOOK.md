# دليل تشغيل عقاري برو — نسخة المالك (Production Runbook)

> حالة الوثيقة: خطة نشر وتشغيل، وليست إثباتًا بأن التطبيق جاهز لاستقبال بيانات العملاء.

## التهيئة المطلوبة
- خادم Linux محدث مع PHP 8.3+ وامتدادات PDO MySQL, mbstring, bcmath, fileinfo, openssl وComposer.
- MySQL 8 مع قاعدة بيانات مستخدمها محدود الصلاحيات؛ لا تُفتح قاعدة البيانات للإنترنت العام.
- Nginx/Apache مع HTTPS فعلي وشهادة صالحة، وجذر المستندات `backend/public` فقط.
- تخزين خاص قابل للكتابة للمرفقات والسجلات والذاكرة المؤقتة، مع نسخ احتياطي مستقل.
- نطاق رسمي وبريد خدمة لإعادة الحساب والتنبيهات، ومراقبة توافر الخدمة.

## قبل أول تشغيل
1. خذ نسخة احتياطية كاملة من قاعدة البيانات الحالية (إن وجدت) والملفات.
2. راجع كود Pull Request #1 ولا تدمجه تلقائيًا.
3. انقل الملفات إلى الخادم بعيدًا عن `public_html`، واجعل المسار العام `backend/public` فقط.
4. نفّذ داخل `backend`: `composer install --no-dev --prefer-dist --optimize-autoloader`.
5. أنشئ `.env` من `.env.example`، ثم عيّن: `APP_ENV=production`, `APP_DEBUG=false`, `APP_URL=https://YOUR_DOMAIN`, `DB_CONNECTION=mysql`, `DB_HOST`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`, `SESSION_SECURE_COOKIE=true`.
6. أنشئ مفتاح تطبيق فريدًا: `php artisan key:generate`. احتفظ به في مدير أسرار آمن ونسخ استعادة مشفرة.
7. تأكد أن مجلدات `storage` و`bootstrap/cache` قابلة للكتابة من حساب PHP دون فتح صلاحية 777.
8. شغّل `php artisan migrate --force` **بعد اختبارها مسبقًا على Staging**.
9. أنشئ حساب المالك تفاعليًا: `php artisan owner:create owner@example.com "اسم المالك"`، واستخدم كلمة مرور قوية.
10. تحقق من `/up`، ومن تسجيل الدخول عبر `/app/index.html`، ومخرجات الاختبارات على staging.

## فحوص الأمان قبل فتح الموقع للعامة
- تطبيق HTTPS وتحويل HTTP إليه، وضبط HSTS بعد التأكد من إعداد الدومين.
- حماية الوصول للمرفقات الخاصة، ومنع تصفح `.env` و`storage` و`vendor`.
- إغلاق تسجيل الأخطاء التفصيلية للعامة مع الاحتفاظ بسجلات خادم قابلة للمراجعة.
- اختبار فصل بيانات مالكين فعليين على Staging باستخدام حسابين مستقلين.
- فحص الملفات المرفوعة ضد البرمجيات الخبيثة وتطبيق حدود التخزين والاحتفاظ.
- تفعيل النسخ الاحتياطي المشفر خارج الخادم، وفحص القدرة على الاستعادة.
- اختبار الضغط والتزامن والانتقال بين حالات العقود والتحصيل والإلغاء.
- إعداد سياسة خصوصية وشروط استخدام بما يتناسب مع بيانات المستأجرين.
- تأكيد عدم الإعلان عن تكامل حكومي فعلي؛ «إيجار» في النسخة العامة محاكاة فقط.

## خطة النسخ الاحتياطي والاستعادة
- قاعدة البيانات: نسخة يومية مشفرة مع نسخة أسبوعية كاملة وتحديد مدة الاحتفاظ بحسب السياسة.
- المرفقات: نسخ متناسقة مع نسخة قاعدة البيانات، لأن سجل المستند وحده لا يحتوي الملف نفسه.
- مفاتيح التطبيق: حفظ آمن منفصل؛ ضياع `APP_KEY` يعطل فك تشفير بعض بيانات التطبيق.
- تمرين استعادة منتظم إلى بيئة منفصلة والتأكد من سلامة العقد، المستند، والسند والتوزيع المالي.
- لا تستخدم `migrate:fresh` أو إعادة تعبئة بيانات Demo على قاعدة الإنتاج.

## معايير القبول النهائية
- استقرار API ومراجعة واجهة المالك على الجوال وسطح المكتب.
- جميع الاختبارات الآلية ناجحة، ثم اختبارات يدوية End-to-End واختبار أداء.
- إكمال استعادة الحساب ومراجعة الأمان وإدارة صلاحيات التشغيل، وتدقيق سجلات المعاملات.
- مراجعة الفواتير والقيود والاستحقاقات والمعالجة المحاسبية للإلغاءات.
- مراقبة، تنبيهات توقف، وخطة استجابة للحوادث.
- اعتماد مالك المنتج للتجربة النهائية، وعمل Go/No-Go واضح قبل الإطلاق.

## الموانع الحالية
لم يتم ربط هذا المستودع بخادم إنتاج، ولم يتم تشغيل قواعد بيانات إنتاجية، ولم يتم اختباره بحمل فعلي أو تدقيق أمني مستقل.
لا توجد مفاتيح وصول استضافة أو بيانات بريد وإعداد نسخ احتياطية ضمن المستودع. لهذا فإن نشر GitHub Pages وحده **لا يعد إطلاقًا إنتاجيًا**.

## فحص تشغيل CI (إضافة)
تتحقق `.github/workflows/backend-ci.yml` الآن من:
- بناء تبعيات Composer، والتحقق من PHP وJavaScript.
- تشغيل مجموعة اختبارات الوظائف والعزل والأمان.
- إنشاء قاعدة SQLite مهاجرة على بيئة مؤقتة، ثم تشغيل Laravel عبر HTTP.
- التأكد من أن `/up` و`/app/index.html` يستجيبان بنجاح.
- التأكد من أن `/api/portfolio` يرفض الطلب غير الموثق بنتيجة HTTP 401.

نتيجة تشغيل CI هذه **ليست إثباتًا لجاهزية الاستضافة الإنتاجية** ولا تغني عن HTTPS الحقيقي وتخزين المرفقات الآمن والنسخ الاحتياطية وتشغيل قواعد البيانات.

## بريد استعادة كلمة المرور
خدمة استعادة كلمة المرور تُرسل عبر SMTP فقط عند الإنتاج. يجب ضبط `MAIL_MAILER=smtp` و`MAIL_HOST` و`MAIL_PORT` و`MAIL_USERNAME` و`MAIL_PASSWORD` و`MAIL_FROM_ADDRESS` صحيحة من مدير الأسرار، مع إثبات نجاح وصول الرسائل وتحديث DNS (SPF/DKIM/DMARC). وضع `MAIL_MAILER=log` أو `array` لا يُقبل في الإنتاج.

## تشغيل عبر Docker Compose — مرجع نشر جديد

في `backend` تتوفر الملفات: `Dockerfile`, `compose.yaml`, `.docker/entrypoint.sh`.
الخطوات تخص **خادمًا مخصصًا أو Staging مع صلاحيات Docker**، وليست أوامر GitHub Pages:

1. تأكد من وجود Docker Engine وCompose plugin، ومن موارد خادم مناسبة ونسخ احتياطي خارجي.
2. ضع الأسرار الحقيقية في ملف بيئة **خارج Git**، ولا تستخدم مفاتيح الاختبارات ولا تضع كلمات مرور في المحادثات.
3. عرّف في بيئة Compose: `APP_KEY`, `APP_URL=https://DOMAIN`, `DB_PASSWORD`, `MYSQL_ROOT_PASSWORD`, `MAIL_MAILER=smtp`, `MAIL_HOST`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_FROM_ADDRESS`.
4. نفّذ `docker compose build`، ثم `docker compose up -d`.
5. نفّذ `docker compose exec app php artisan migrate --force` بعد اختبار الترحيلات في Staging.
6. أنشئ حساب المالك عبر `docker compose exec app php artisan owner:create owner@example.com "اسم المالك"`.
7. ضع **Reverse Proxy مع TLS/HTTPS** أمام التطبيق الذي لا يستمع إلا على `127.0.0.1:8080`. يجب التأكد من تمرير الأصل والـ headers بصورة آمنة.
8. افحص `/up`, `/app/index.html` وتسجيل الدخول والاستعادة والمرفقات، وتأكد أن `/api/portfolio` يعيد 401 دون رمز مصادقة.
9. لا تنقل بيانات حقيقية قبل اختبار الأداء والنسخ الاحتياطية ومراجعة الأمان.

الملف `backend/compose.yaml` يستخدم مجلدين مستمرين: `mysql_data` و`private_storage`. حذف أحجام Docker قد يمحو البيانات؛ لا تستخدم `docker compose down -v` على بيانات حقيقية.

## النسخ الاحتياطي المشفر
نص النسخ: `backend/scripts/backup-encrypted.sh`. يحتاج على خادم التشغيل: Docker Compose، وBash، و`age`، و`gzip`، و**مفتاح استقبال age عام** (`AGE_RECIPIENT`).
بعد ضبط المتغيرات، شغّل من مجلد `backend`:
`AGE_RECIPIENT=age1... BACKUP_DIR=/secure/offsite-stage bash scripts/backup-encrypted.sh`.

النسخ تنشئ ملفًا مشفرًا لقاعدة MySQL وآخر للمرفقات الخاصة، ويتوقف HTTP مؤقتًا خلال النسخ ثم يُعاد تشغيله عند الخروج. النسخ المحلي لا يكفي؛ انقل الملفات المشفرة إلى وجهة مستقلة واختبر فكها واستعادتها **داخل Staging معزول**. لا تضع المفتاح الخاص لفك التشفير على نفس خادم قاعدة البيانات. لا تُعتبر ميزة النسخ الاحتياطي مكتملة تشغيليًا دون اختبار استعادة دوري موثق.

## اختبار آلي لاستعادة النسخ المشفرة (CI)

أضيف `backend/scripts/ci-backup-restore-drill.sh` إلى مسار `.github/workflows/backend-container-ci.yml` للتحقق من:
1. بدء حاويتَي Laravel وMySQL مع تنفيذ الترحيلات.
2. وضع سجل اختباري داخل MySQL ومستند اختباري خاص داخل مجلد التخزين.
3. توليد مفتاح `age` مؤقت لتشفير نسخة قاعدة البيانات وملفات المرفقات.
4. تشغيل `scripts/backup-encrypted.sh` مع تفعيل وضع الصيانة المؤقت.
5. فك التشفير واستيراد قاعدة البيانات إلى قاعدة اختبار **منفصلة** عن الأصل والتحقق من استرجاع السجل الاختباري.
6. استخراج أرشيف المرفقات إلى مجلد مستقل والتحقق من محتوى الملف.
7. التأكد من عودة استجابة `/up` ثم حذف بيئة الاختبار المؤقتة.

**ضابط مهم:** النص مخصص لحاويات GitHub Actions المؤقتة ولا يعمل خارج بيئة CI. لا يشغّل أبدًا على قاعدة إنتاج، ولا يختبر نسخًا احتياطية خارج الخادم أو استعادة الكارثة على استضافة مختلفة. حتى بعد نجاحه يجب تشغيل تمرين استعادة مستقل على Staging مع بيانات اصطناعية قبل الإطلاق التجاري.


## فحص المرفقات قبل الإطلاق

- يتطلب الإنتاج وجود ClamAV قابل للتنفيذ في مسار `DOCUMENT_CLAMSCAN_BINARY` داخل الحاوية الفعلية التي تستقبل ملفات الرفع.
- يجب تثبيت قاعدة تواقيع الفيروسات وتحديثها دوريًا باستخدام `freshclam` قبل قبول أي وثائق حقيقية.
- عند تعطل الماسح أو انتهاء المهلة أو غيابه يرفض API الرفع برمز 503 **دون كتابة الملف في تخزين المالك**؛ هذا السلوك مقصود وليس خللًا في الواجهة.
- تفعيل `DOCUMENT_SCAN_ENABLED=true` يفيد بيئة Staging، بينما الإنتاج يفرض الفحص مهما كانت قيمة المتغير.
- الإعدادات: `DOCUMENT_CLAMSCAN_BINARY=/usr/bin/clamscan` و`DOCUMENT_SCAN_TIMEOUT=30`. ينبغي تأمين الموارد لأن استدعاء `clamscan` لكل رفع أعلى تكلفة من خدمة `clamd` المستمرة.
- فحص ClamAV إجراء دفاعي إضافي ولا يغني عن العزل والتخزين الخاص وحدود الحجم والنسخ الاحتياطية ومراجعة أنواع الملفات.
- **لا يثبت وجود هذه الشيفرة أن ClamAV مُثبت في الاستضافة أو أن التواقيع محدثة**؛ يلزم فحص رفع حقيقي آمن على Staging قبل الإطلاق.


### بوابة فحص جاهزية ClamAV قبل فتح الرفع للعملاء
بعد بناء الحاوية وتشغيلها، حدّث قاعدة التواقيع داخل الحاوية باستخدام `docker compose exec -u root app freshclam` (مع التأكد من الشبكة وإدارة قواعد التحديث والجدولة). ثم نفّذ من مجلد `backend`:

```bash
docker compose exec -T app bash scripts/check-clamav-readiness.sh
```

يتحقق هذا الفحص من وجود `clamscan`، ووجود قاعدة `main` أو `daily` ضمن `/var/lib/clamav` محدّثة خلال آخر 72 ساعة، وقدرة الماسح على فحص ملف آمن مؤقت. يمكنك تخصيص `CLAMAV_DATABASE_DIR` و`CLAMAV_MAX_SIGNATURE_AGE_HOURS`. **الفشل يمنع اعتماد الإطلاق أو فتح رفع المرفقات**؛ نجاح بناء الحاوية وحده لا يعني وجود توقيعات محدثة. يجب وضع عملية تحديث تواقيع مجدولة ومراقبة فشلها في بيئة التشغيل، ولا تعتمد على تحديث يدوي وحيد.

`GitHub Actions` يفحص صياغة أداة التحقق ويرفض حالة التواقيع المفقودة اصطناعيًا؛ لا يدّعي أنه نفّذ تحديثًا حقيقيًا للتواقيع على خادم العملاء.


## اختبار التزامن والتحصيل على Staging

أضيف `backend/scripts/staging-receipt-concurrency.cjs` لاختبار ثلاثة سيناريوهات باستخدام طلبات HTTP متزامنة حقيقية على **Apache وMySQL في بيئة تجريبية معزولة**، وليس `php artisan serve` أحادي التنفيذ:

1. إرسال 8 طلبات تحصيل بالمفتاح نفسه: يُنشأ سند واحد فقط (201) وبقية الطلبات تعيد السند نفسه (200).
2. إرسال 8 طلبات بمفاتيح مختلفة على عقد يكفي رصيده سندًا واحدًا: ينجح سند واحد فقط وتُرفض البقية (422).
3. إرسال 8 طلبات لإنشاء عقود متداخلة على الوحدة نفسها: يُنشأ عقد واحد وترفض بقية العقود (422).

شغّل بعد إنشاء **حساب اختبار مستقل** على Staging وتهيئة Apache/MySQL من مجلد `backend`:

```bash
AQARI_CONCURRENCY_WRITES=staging-only \
AQARI_CONCURRENCY_URL=https://staging.example.invalid \
AQARI_CONCURRENCY_REMOTE=staging-confirmed \
AQARI_CONCURRENCY_EMAIL=test-owner@example.invalid \
AQARI_CONCURRENCY_PASSWORD='REPLACE_WITH_STAGING_SECRET' \
AQARI_CONCURRENCY_REQUESTS=8 \
node scripts/staging-receipt-concurrency.cjs
```

السكربت يرفض التشغيل دون التصريح بالكتابة وبيانات الدخول، ويشترط HTTPS للنطاقات غير المحلية ويرفض أسماء المضيفين الظاهرة كبيئة إنتاج. رغم ذلك، **مسؤولية التأكد من أن الرابط Staging فعلية تقع على المشغّل**. لا تستخدم حسابًا حقيقيًا ولا قاعدة إنتاج لأن الاختبار يُنشئ سجلات عقارات ومستأجرين ووحدات وعقود وسندات اختبارية ولا يحذفها تلقائيًا.

تحقق CI من صياغة JavaScript فقط؛ **نجاح اختبار التزامن الفعلي يتطلب تشغيل السكربت على بيئة Staging متعددة العمليات** وفحص نتائجه. احتفظ بنتائج الاختبار ضمن محضر اعتماد Go/No-Go قبل الإطلاق.


## قياس أداء القراءة على Staging

تتوفر أداة `backend/scripts/staging-read-performance.cjs` لقياس استجابة واجهات القراءة الأساسية على Staging بحساب مالك تجريبي. تستعلم الأداة فقط عن `overview` و`portfolio` و`units` و`leases` و`payments` و`documents`، ولا تنشئ بيانات جديدة. تُظهر عدد الأخطاء ومقاييس P50/P95/P99، وترفض نتيجة تتجاوز الحد المحدد.

شغّل في مجلد `backend` باستخدام Node.js 20+:

```bash
AQARI_PERF_ACK=staging-only \
AQARI_PERF_REMOTE=staging-confirmed \
AQARI_PERF_URL=https://staging.example.invalid \
AQARI_PERF_EMAIL=test-owner@example.invalid \
AQARI_PERF_PASSWORD='REPLACE_WITH_STAGING_SECRET' \
AQARI_PERF_REQUESTS=40 \
AQARI_PERF_PARALLEL=4 \
AQARI_PERF_P95_MS=2000 \
node scripts/staging-read-performance.cjs
```

يقيد السكربت الإجمالي إلى 6–300 طلبًا والتوازي إلى 1–10 طلبات، ويتطلب موافقة صريحة لتشغيله على Staging وعنوان HTTPS للبيئات غير المحلية. يجب ألا تستخدمه على الإنتاج ولا بحساب يحتوي بيانات عملاء. **CI يتحقق من صياغة JavaScript، ولا يثبت أداء الخادم الفعلي**؛ احتفظ بنتيجة تشغيل Staging وقارنها بالحدود المعتمدة قبل قرار Go/No-Go.


## اختبار التزامن والأداء الفعلي ضمن CI

تُشغّل `.github/workflows/backend-container-ci.yml` الآن اختبارَي `staging-receipt-concurrency.cjs` و`staging-read-performance.cjs` بعد إقلاع Apache/MySQL في حاويات GitHub Actions المؤقتة. ينشئ الفحص حساب مالك تجريبي بواسطة `BrowserSmokeSeeder` مع فرض `APP_ENV=testing` لذلك الأمر فقط، ثم يتحقق من:

- عدم تكرار سند قبض عند إرسال أربعة طلبات متوازية بالمفتاح نفسه.
- منع إنشاء سندات تتجاوز رصيد العقد عند تنافس أربعة طلبات بمفاتيح مختلفة.
- منع تداخل أربعة عقود على وحدة واحدة تحت التزامن.
- أداء 24 طلب قراءة بتوازٍ قدره أربعة، دون أخطاء HTTP، وبحد قبول `P95 ≤ 5000ms` لهذا الفحص الأولي فقط.

هذا **اختبار تكامل لحاويات مؤقتة** وليس قياس أداء إنتاجيًا ولا يغني عن تشغيل سيناريوهات الحمل على Staging مستقل ببيانات اصطناعية، أو فحص استقرار الحاوية والنسخ الاحتياطي. فشل الاختبار يمنع قبول PR حتى معالجة سبب التزامن أو الأداء.


## تدقيق HTTP الأمني الآلي

يُنفّذ فحص `backend/scripts/check-http-security.sh` بعد بدء Apache وMySQL في GitHub Actions، ويتأكد من أن مسارات ملفات البيئة وGit وتبعيات Composer وملفات التخزين الخاص والسجلات تُرجع 403/404، وأن واجهات بيانات الملاك والمرفقات ترفض الوصول غير الموثّق بنتيجة 401، وأن صفحة المالك تتضمن ترويسات `nosniff` و`X-Frame-Options: DENY`.

يمكن تكرار الفحص على Staging بعد ضبط `AQARI_SECURITY_BASE_URL` إلى عنوان HTTPS اختباري. لا يشمل هذا الفحص تدقيق OWASP كاملًا، ولا يغني عن اختبار الوصول بين ملاك متعددين، ومراجعة Reverse Proxy وTLS ومراقبة الحوادث قبل الإطلاق.


## اختبار انحدار جاهزية برنامج الحماية

يتضمن CI فحصًا حتميًا في `backend/scripts/ci-clamav-readiness-drill.sh` لأربع حالات باستخدام ملفات تجريبية غير حقيقية: غياب التواقيع، انتهاء صلاحية حداثتها، نجاح فحص عينة آمنة، وفشل عملية الفحص. يُمنع قبول الحالة غير الآمنة، ويُسمح بالجاهزية التجريبية فقط عند وجود ملف تواقيع حديث وعمل الماسح التجريبي بنجاح. هذا اختبار لمسار التحقق وليس إثباتًا لصحة تواقيع ClamAV الحقيقية أو تحديثها على الخادم.


## بوابة تحقق Staging من نسخة الإصدار المنشورة

بعد تجهيز **خادم Staging منفصل** ونشر النسخة المختبرة وتحديث تواقيع ClamAV الحقيقية، يمكن تنفيذ الفحص التالي داخل مجلد `backend` على خادم Staging نفسه:

```bash
AQARI_STAGING_APPROVED=staging-only \
AQARI_STAGING_URL=https://staging.your-domain.example \
AQARI_EXPECTED_SHA=PUT_FULL_40_CHARACTER_TESTED_COMMIT_SHA_HERE \
bash scripts/staging-verify.sh
```

الأداة تقرأ فقط، ولا تُجري `migrate` أو `seed` أو `freshclam` أو تغيّر قاعدة البيانات. تتحقق من SHA المستودع المطابق للإصدار المعتمد، من قوالب Docker Compose وتشغيل حاويتَي التطبيق والقاعدة، من عنوان HTTPS وفحوص عدم كشف الملفات الخاصة، من رفض API غير الموثق، ومن وجود تواقيع ClamAV حديثة ونجاح فحص عينة آمنة، ومن قابلية عرض حالة الترحيلات. **التحقق من SHA المحلي لا يثبت وحده مطابقة الصورة المبنية للنشر؛ يجب تسجيل SHA الصورة وعملية النشر مع سجل الاعتماد.**

قبل تشغيل الأداة يجب ضبط `AQARI_STAGING_APPROVED=staging-only` فقط بعد التأكد البشري أن الرابط يخص بيئة Staging ولا يحوي بيانات عملاء. لا تستخدم نطاق الإنتاج. نتيجة PASS لا تشمل نجاح توصيل البريد، ولا استعادة نسخة خارجية، ولا فصل مالكين حقيقيين، ولا أداء حجم بيانات مشابه للإنتاج؛ هذه اختبارات منفصلة واجبة ضمن `docs/OWNER_V1_RELEASE_GATES.md`.


### منع اعتماد صورة Docker قديمة أو ترحيلات معلّقة
يُطابق فحص `staging-verify.sh` الآن بصمات SHA-256 لملفات `artisan` و`composer.lock` و`routes/api.php` و`scripts/staging-verify.sh` بين نسخة Git المعتمدة وصورة التطبيق العاملة داخل الحاوية. كما يفحص نتيجة `php artisan migrate:status` ويرفض الاعتماد عند وجود ترحيلات `Pending` أو عدم العثور على ترحيلات `Ran`. هذه فحوص **عدم التطابق الجزئي** وليست إثباتًا كاملًا لسلامة كافة طبقات الصورة؛ يُنصح مع ذلك بتسجيل digest للصورة المنشورة ومراجعة مصدر بنائها. لا تشغّل الترحيلات تلقائيًا أثناء خطوة التحقق؛ عالج أي `Pending` أولًا ضمن خطة نشر معتمدة.
